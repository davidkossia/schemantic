# Schemantic plan

Schemantic is a 2026 rebuild of NexusAgents, an earlier project of mine whose repository was lost. This file is the build plan. The README describes what exists today.

## Goal

A multi-agent system that takes a question plus an image (a circuit schematic or a graph) and helps solve it:

1. A **reader** agent turns the image into structured data.
2. A **person** checks and corrects that data before anything is solved.
3. A **solver** agent reasons over the approved data and calls deterministic tools for the math.
4. A **checker** verifies the answer numerically before it is shown.
5. Every phase streams to the browser over WebSockets.

The project must run and show the work. It does not need to be perfect.

## Architecture

```
browser (React + Tailwind)  <-- WebSocket -->  Node server (ws)
                                                 |
                       +-------------------------+-------------------------+
                       |                         |                         |
                  reader agent              solver agent               checker
                  (Claude, vision,          (Claude + tools:           (pure code:
                   zod structured output)    solve_circuit, evaluate,   KCL residuals,
                                             graph_query, submit)       units, tolerance)
                                                 |
                                           core/ (no model calls)
                                           MNA solver, unit parser, graph tools
```

- `src/core` has no model calls. It holds the zod schemas, the unit parser, the modified nodal analysis (MNA) solver, the graph tools and the checker. Every number that reaches the user comes from this code.
- `src/agents` wraps the Anthropic SDK. The model is `claude-opus-5-5`. Requests use `fallbacks: "default"` with the `server-side-fallback-2026-07-01` beta, so a safety refusal retries on a fallback model.
- `src/server` is an HTTP + WebSocket server. One session per socket.
- `web` is the Vite + React + Tailwind client.

### Message protocol

Client to server: `start` (image, question), `approve` (edited structure), `cancel`.
Server to client: `phase`, `parsed`, `awaiting_review`, `solving`, `token`, `step`, `check`, `done`, `error`.

### Why the split

- **Vision is the weak link.** A misread resistor value gives a confident, wrong answer. The human check catches it before the solver runs, and the schematic redrawn from the parsed data makes a misread easy to see.
- **Models are unreliable at arithmetic.** The solver agent decides what to compute. Code computes it.
- **The checker is independent.** It re-solves the circuit from the approved netlist and compares against what the solver agent submitted. It does not trust the agent's numbers or its own earlier tool output.

## Eval design

- **Set:** 18 problems. 14 circuits (voltage dividers, series and parallel networks, ladders, a bridge, circuits with current sources, node voltage, branch current and power questions) and 4 graph problems (value at x, slope, area, maximum).
- **Images:** generated by `eval/render.ts` from each problem's ground-truth data, drawn as SVG and rasterized to PNG. No third-party images, so there is no licence to track.
- **Known answers:** each problem stores a hand-derived answer (closed-form formula written in the problem file). The tests check the MNA solver against these formulas, so the solver is not graded against itself.
- **Metrics:**
  - *Parse accuracy:* the share of ground-truth components that the reader returns with the right type, value, unit and nodes (circuits), or the share of series points within tolerance (graphs). Reported with precision, so extra components count against it.
  - *Final-answer accuracy:* the share of problems whose final answer is within 1% of the known answer, with the reader's output approved unedited.
  - *Solver-only accuracy:* the same, with the ground-truth structure fed in. This runs without a key and isolates the solver from the reader.
- **Limits:** generated images are cleaner than photos. The numbers show the pipeline works on clean drawings. They do not predict accuracy on hand-drawn or photographed circuits.

## Costs (estimates)

Opus 5.5 lists at $4 per million input tokens and $20 per million output tokens. A reader call is about 3,000 input and 4,000 output tokens (image, prompt, reasoning, netlist). A solver run is about 3 to 5 turns. That puts one problem at roughly $0.15 to $0.25 and the full 18-problem eval at roughly $3 to $5. Prompt caching on the fixed system prompts trims this slightly. The first measured run replaces these estimates.
